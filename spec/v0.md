# air request format, version 0

A **request** is a GitHub issue that describes a piece of AI work completely enough that a colleague's
agent, on their machine, can do it without asking questions. `air serve` acts on requests by reading two
things only: the **front matter** and the **section headings**. Free text never changes what a server does;
it is for the agent.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Issue

A request is an open issue labelled `ai-request` whose body is:

1. a front-matter block: a line `---`, YAML (§3), a line `---`. Only blank lines may precede it;
2. Markdown sections (§4).

Bodies are read after removing a UTF-8 BOM and turning CRLF/CR line endings into LF. Line numbers in
diagnostics count from 1 at the first line of the body.

Servers MUST only act on issues, comments and labels written by accounts with write access to the
requests repo: `setup` and `check` are shell commands run on the server's machine.

## 2. Fields

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `air` | yes | integer | Spec version. This document is `0`. |
| `effort` | yes | `XS` \| `S` \| `M` \| `L` \| `XL` | Expected cost as a share of one weekly usage window: 1, 3, 8, 20, 40 %. |
| `harness` | no | list of `claude` \| `codex` \| `any` | Harnesses that may run it. Default `[any]`. `any` cannot be combined with others. A single value is read as a one-item list. |
| `model` | no | `small` \| `medium` \| `large` | Minimum model tier. Default `medium`. |
| `context` | no | map `url`, `sha256`, `bytes` (all required) | A zip of input files (§5). |
| `repo` | no | map `url`, `ref` (both required) | Git repo to check out. `url` is an `https://` clone URL; `ref` a branch, tag or commit. |
| `setup` | no | list of strings | Shell commands run in order before the agent starts (§5). |
| `check` | no | string | One shell command; exit status 0 means setup worked. |
| `deliver` | yes | `comment` \| `pr` \| `artifact` | How the result comes back (§6). `pr` requires `repo`. |
| `deadline` | no | `YYYY-MM-DD` or RFC 3339 date-time with offset | Don't start after this. A bare date means 23:59:59Z that day. |
| `timeout` | no | duration `<n>h`, `<n>m` or `<n>h<n>m` | Wall-clock limit for the agent, 1m to 24h. Default `4h`. |

Unknown keys, at the top level or inside `context`/`repo`, are errors, so typos never silently drop a field.

**Model tiers** name a class, not a model: `small` is Haiku class, `medium` Sonnet class, `large` Opus
class. Each server maps tiers to its own harness's models in local configuration; a server MUST NOT run a
request on a model below the requested tier.

**Effort** is the requester's estimate. A server claims a request only if its remaining quota covers the
effort's share with headroom; how it measures quota is not part of this spec.

## 3. YAML subset

The front matter is YAML 1.2 restricted to the forms below. Anything else is an error, so that every valid
request means the same thing to air and to any YAML parser.

- `key: value` lines; keys match `[A-Za-z_][A-Za-z0-9_-]*` and appear at most once per map.
- Indentation is spaces only. A key with no value on its line opens a block, which is either
  - a **block list**: `- item` lines, all at the same indent (equal to or deeper than the key), or
  - a **nested map**: `key: value` lines all at the same deeper indent. Maps nest one level only; a
    nested key's value is a scalar (or a list, which v0 fields reject).
- **Flow lists** on one line: `[a, b]`, `["x, y", z]`, `[]`. No flow maps (`{}`).
- **Scalars**:
  - plain: runs to end of line. It MUST NOT start with any of `[ ] { } , & * ! | > % @ `` ` `` `" ' #`
    or with `- `, `? `, `: `, and MUST NOT contain `: ` or end in `:`. Inside a flow list it also cannot
    contain `,` `[` `]` `{` `}`. Quote anything else.
  - `"double quoted"`: escapes `\"` `\\` `\/` `\n` `\t` `\r` `\0` `\uXXXX`.
  - `'single quoted'`: `''` is a literal `'`; no other escapes.
- Comments: a line whose first non-space character is `#`, or ` #` after a plain or quoted value.
- No multi-line strings (`|`, `>`), anchors, aliases, tags or documents.

All values are strings except where §2 says integer (`air`, `context.bytes`), which MUST be unquoted digits.
`true`, `null`, `1.5` etc. are just strings and then fail field validation if the field doesn't accept them.

## 4. Sections

Level-2 ATX headings (`## Title`, case-insensitive) outside fenced code blocks and HTML comments split the
body. A section's text runs to the next level-1 or level-2 heading.

| Section | Required | Contents |
| --- | --- | --- |
| `## Task` | yes | What to do, written for an agent that has never met the requester. |
| `## Done when` | yes | A Markdown list of checkable acceptance criteria. |
| `## Context` | if `context` or `repo` is set | What is in the zip / repo and where to look. |
| `## Notes` | no | Anything else: constraints, style, known pitfalls. |

Required sections MUST be non-empty (HTML comments don't count). Each section appears at most once. Other
`##` headings are allowed and reach the agent, but `air lint` warns about them.

## 5. Workspace

The server creates a fresh directory `$AIR_WORKSPACE` with:

| Path | Contents |
| --- | --- |
| `repo/` | `repo.url` cloned and checked out at `repo.ref` (only if `repo` is set). |
| `context/` | the `context` zip, extracted (only if `context` is set). |
| `out/` | empty; files the agent leaves here are the artifact for `deliver: artifact`. |
| `request.md` | the issue body as claimed. |

The context zip is either a GitHub issue attachment (≤ 25 MB) or a release asset (≤ 2 GiB). The server MUST
verify `bytes` and `sha256` before extracting and fail the request (§7) on mismatch.

`setup` commands and `check` run with `sh -c`, in `repo/` if `repo` is set, else in `$AIR_WORKSPACE`, with
`AIR_WORKSPACE`, `AIR_CONTEXT` (`$AIR_WORKSPACE/context`) and `AIR_OUT` (`$AIR_WORKSPACE/out`) set. A
non-zero exit from any `setup` command or from `check` fails the request before the agent starts. When
setup passes, the server starts the agent at once, in the same directory, with the body as its brief.

The server snapshots the body when it claims; edits made while the issue is claimed are ignored.

## 6. Delivery

- `comment`: the agent's final report is posted as an issue comment.
- `pr`: the server pushes a branch `air/<issue-number>` and opens a pull request against `repo.url` with
  base `repo.ref` (which MUST then be a branch), linking the issue. The PR is the deliverable; a summary
  comment links it.
- `artifact`: the server zips `out/` and uploads it as an asset named `air-<issue-number>-<nonce>.zip` on
  the release tagged `air-artifacts` in the requests repo, then comments the asset's `url`, `sha256` and
  `bytes` (the same shape as `context`).

## 7. Labels

| Label | Set by | Meaning |
| --- | --- | --- |
| `ai-request` | requester | This issue is a request. Required. |
| `air:claimed` | server | A server won the claim (§8) and is setting up. |
| `air:running` | server | Setup passed; the agent is running. |
| `air:paused` | server | The agent was stopped (operator, quota, reboot); workspace and claim are kept. Back to `air:running` on resume. |
| `air:done` | server | Delivered. The server closes nothing; the requester closes the issue. |
| `air:failed` | server | Setup, check, download, timeout or the agent failed. The server comments why and releases the claim. |
| `air:cancel` | requester | Stop and release. |

Flow: `ai-request` → `air:claimed` → `air:running` ⇄ `air:paused` → `air:done` | `air:failed`. A server
replaces one state label with the next; at most one of `air:claimed`, `air:running`, `air:paused`,
`air:done`, `air:failed` is present.

A server MAY claim an issue only if it is open, has `ai-request`, has none of the labels above, is
not past its `deadline`, and no claim currently holds it (§8).

On `air:cancel` the holding server stops the agent, removes its state label, posts a release (§8) and
leaves `air:cancel` in place. No server claims an issue with `air:cancel`; the requester removes it (and
`air:failed`, to retry a failure) to offer the issue again.

## 8. Claiming

Servers coordinate through hidden markers in issue comments. `<host>` matches `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`,
`<nonce>` is 8 to 64 random `[A-Za-z0-9]` characters, fresh per claim.

```
<!-- air-claim v0 host=<host> nonce=<nonce> -->
<!-- air-release v0 host=<host> nonce=<nonce> -->
<!-- air-unsupported v0 host=<host> air=<n> -->
```

1. To claim, a server posts a comment containing an `air-claim` marker plus a human-readable line, waits at
   least 10 seconds, and re-reads the comments.
2. The **holder** is the earliest (lowest comment id) `air-claim` that isn't ended by a later `air-release`
   with the same host and nonce. Claims posted while another claim holds are ignored.
3. If it holds, the server adds `air:claimed` and proceeds. If not, it deletes its claim comment and
   moves on.
4. When a server gives up an issue (failure, cancel, operator release) it posts an `air-release` for its
   claim. `air:done` issues are not released.

## 9. Versioning

Every change to this format, however small, increments `air`. A server MUST NOT act on a request whose
`air` is greater than the newest version it implements. Instead it posts, once per host and version, a
comment with an `air-unsupported` marker saying which version it understands, and otherwise ignores the
issue. A server SHOULD keep accepting older versions it implements.
