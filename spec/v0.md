# air request format, version 0

A **request** is a GitHub issue that describes a piece of AI work completely enough that a colleague's
agent, on their machine, can do it without asking questions. `air serve` acts on requests by reading two
things only: the **front matter** and the **section headings**. Free text never changes what a server does;
it is for the agent.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Issue

A request is an open issue labelled `ai-request` whose body is:

1. a front-matter block: a line `---`, YAML (§3), a line `---`. Only blank lines may precede it;
2. Markdown sections (§4).

Bodies are read after removing a UTF-8 BOM and turning CRLF/CR line endings into LF. Line numbers in
diagnostics count from 1 at the first line of the body.

Servers MUST only act on issues, comments and labels written by accounts with write access (write,
maintain or admin) to the requests repo: `setup` and `check` are shell commands run on the server's
machine. A server decides this from the item's `author_association`: `OWNER` is trusted; `MEMBER` and
`COLLABORATOR` are ambiguous (org members and collaborators may be read-only), so the server checks
`gh api repos/{owner}/{repo}/collaborators/{login}/permission`; anything else is untrusted.

Servers MUST run `git`, `curl`, `gh` and every other program they start themselves with an argv array,
never through a shell. Only `setup` and `check` go through `sh -c`, because they are shell commands.

## 2. Fields

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `air` | yes | integer | Spec version. This document is `0`. |
| `effort` | yes | `XS` \| `S` \| `M` \| `L` \| `XL` | Expected cost in US dollars at API prices: XS $1, S $3, M $10, L $30, XL $100. |
| `harness` | no | list of `claude` \| `codex` \| `any` | Harnesses that may run it. Default `[any]`. `any` cannot be combined with others. A single value is read as a one-item list. |
| `model` | no | `small` \| `medium` \| `large` | Minimum model tier. Default `medium`. |
| `context` | no | map `url`, `sha256`, `bytes` (required), `expires` (optional `YYYY-MM-DD`) | A zip of input files (§5, §7). |
| `repos` | no | list of maps (below) | Git repos to check out, each in its own folder under `repo/`. Omit for none. |
| `resume` | no | map `branches`, `out` (below) | Where an earlier claim's checkpoint left off (§11). Written by `air retry`. |
| `setup` | no | list of strings | Shell commands run in order before the agent starts (§5). |
| `check` | no | string | One shell command; exit status 0 means setup worked. |
| `deliver` | yes | `comment` \| `pr` \| `artifact` | How the result comes back (§6). `pr` requires a `repos` entry without `deliver: none`. |
| `deadline` | no | `YYYY-MM-DD` or RFC 3339 date-time with offset | Don't start after this. A bare date means 23:59:59Z that day. |
| `timeout` | no | duration `<n>h`, `<n>m` or `<n>h<n>m` | Wall-clock limit for the agent, 1m to 24h. Default `4h`. |

Unknown keys, at any level, are errors, so typos never silently drop a field.

`context.url`, every `repos` entry's `url` and `resume.out.url` MUST match
`https://<host>[:<port>][/<path>]`, where `<host>` is letters, digits, `.` and `-`, and `<path>` uses only
letters, digits and `. - _ ~ % + = @ : , / ?`. So no whitespace, quotes, `&`, `;`, `$`, backticks, `#`, or
userinfo. Percent-encode anything else.

**Repos.** Each entry of `repos` is a map:

| Key | Required | Meaning |
| --- | --- | --- |
| `url` | yes | `https://` clone URL. |
| `ref` | one of `ref`, `pr` | A branch, tag or commit to check out. |
| `pr` | one of `ref`, `pr` | A pull request number (unquoted integer): check out `refs/pull/<pr>/head` of `url`. |
| `path` | no | Folder under `repo/`. Defaults to the last segment of `url`'s path without `.git` (`https://github.com/o/billing.git` → `billing`). |
| `deliver` | no | Only `none`: the repo is read-only. It is never pushed and needs no permission check. Omitted, the repo is delivered as the request's `deliver` says. |

```yaml
repos:
  - url: https://github.com/acme/billing-service.git
    ref: main
    path: service
  - url: https://github.com/acme/api-guidelines.git
    pr: 41
    deliver: none
```

Exactly one of `ref` and `pr` is set. A `path` is one or more segments separated by `/`. Each segment matches
`[A-Za-z0-9_][A-Za-z0-9._-]*`, so there are no absolute paths, `.` or `..` segments, hidden folders or
leading `-`. Paths MUST be unique when compared case-insensitively (macOS file systems ignore case), and no
path may lie inside another (`a` and `a/b`). Set `path` explicitly when two entries would get the same
default, for example the same repo at two refs. The same `url` may appear more than once.

With `deliver: pr`, at least one entry MUST lack `deliver: none`. Every such entry MUST use `ref`, and that
`ref` MUST be a branch, because each one gets a pull request against it (§6). A `pr` entry can only be
read-only. `air lint` warns when such a `ref` looks like a full commit SHA. With `deliver: comment` or
`artifact` nothing is pushed, so `deliver: none` changes nothing there.

**Resume.** `resume` is written by `air retry` (§12) from a `partial` result (§10), never by hand:

```yaml
resume:
  branches:              # one per repo that has a checkpoint branch
    - repo: service      # a `repos` entry's `path`
      branch: air/12
      sha: "0e3c…"       # 40 or 64 lowercase hex digits; quote it
  out:                   # the checkpoint's out/, zipped: same keys and rules as `context`, no `expires`
    url: https://github.com/<owner>/<requests-repo>/releases/download/air-artifacts/air-12-<nonce>-out.zip
    sha256: <64 lowercase hex>
    bytes: <size>
```

It has at least one `branches` entry, an `out`, or both. Each `branches` entry names, by `path`, a `repos` entry without
`deliver: none`, at most once. `branch` is a valid branch name, and `sha` is the full commit SHA that the
checkpoint pushed there.

**Model tiers** name a class, not a model: `small` is Haiku class, `medium` Sonnet class, `large` Opus
class. Each server maps tiers to its own harness's models in local configuration; a server MUST NOT run a
request on a model below the requested tier.

**Effort** is the requester's estimate of what the job will cost: the tokens its agent uses, priced at
the model provider's published API rates, whatever plan the server actually pays with. A server claims a
request only if what its quota has left, in the same dollars, covers the effort's cost with headroom. How
it measures its quota and converts it to dollars is not part of this spec.

## 3. YAML subset

The front matter is YAML 1.2 restricted to the forms below. Anything else is an error, so that every valid
request means the same thing to air and to any YAML parser.

- `key: value` lines; keys match `[A-Za-z_][A-Za-z0-9_-]*` and appear at most once per map.
- Indentation is spaces only. A key with no value on its line opens a block, which is either
  - a **block list**: `- item` lines, all at the same indent (equal to or deeper than the key). An item
    is a scalar, or a map written `- key: value`, with the map's other keys on the following lines,
    aligned with the first key, or
  - a **nested map**: `key: value` lines all at the same deeper indent.
- Blocks nest only as deep as the fields in §2 need (`resume.branches` is the deepest). A list item can't
  itself be a list (`- - x`, `- [x]`), and an item can't be an empty `-` followed by an indented map.
- **Flow lists** on one line, of scalars only: `[a, b]`, `["x, y", z]`, `[]`. No flow maps (`{}`).
- **Scalars**:
  - plain: runs to end of line. It MUST NOT start with any of `[ ] { } , & * ! | > % @ `` ` `` `" ' #`
    or with `- `, `? `, `: `, and MUST NOT contain `: ` or end in `:`. Inside a flow list it also cannot
    contain `,` `[` `]` `{` `}`. Quote anything else.
  - `"double quoted"`: escapes `\"` `\\` `\/` `\n` `\t` `\r` `\0` `\uXXXX`.
  - `'single quoted'`: `''` is a literal `'`; no other escapes.
- Comments: a line whose first non-space character is `#`, or a `#` preceded by whitespace after a value.
  `a#b` is the plain scalar `a#b`; `"a"#b` is an error.
- No multi-line strings (`|`, `>`), anchors, aliases, tags or documents.

All values are strings except where §2 says integer (`air`, `context.bytes`, `pr` in `repos`,
`resume.out.bytes`), which MUST be unquoted digits. In every other field, an unquoted value that the YAML
1.2 core schema reads as something other than a string is an error, and the author must quote it. That
covers null (`null`, `Null`, `NULL`, `~`), booleans (`true`, `false` in those three casings), integers
(`12`, `-3`, `0x1F`, `0o17`) and floats (`1.10`, `.5`, `1e3`, `.inf`, `.nan`). For example, write
`ref: "1.10"`, `check: "100"`, `setup: ["true"]`, and quote every commit SHA, since one made only of digits
is an integer. YAML 1.1 spellings such as `yes`, `on` or `1_000` are plain strings.

## 4. Sections

Level-2 ATX headings (`## Title`, case-insensitive) outside fenced code blocks and HTML comments split the
body. A section's text runs to the next level-1 or level-2 heading.

| Section | Required | Contents |
| --- | --- | --- |
| `## Task` | yes | What to do, written for an agent that has never met the requester. |
| `## Done when` | yes | A Markdown list of checkable acceptance criteria. |
| `## Context` | if `context` or `repos` is set | What is in the zip and repos, and where to look. |
| `## Notes` | no | Anything else: constraints, style, known pitfalls. |

Required sections MUST be non-empty, and text inside HTML comments doesn't count. A comment that opens
anywhere, including on the heading line itself, hides everything up to its `-->`. An unclosed comment
hides the rest of the body. Each section appears at most once. Other
`##` headings are allowed and reach the agent, but `air lint` warns about them.

## 5. Workspace

The server creates a fresh directory `$AIR_WORKSPACE` with:

| Path | Contents |
| --- | --- |
| `repo/<path>/` | each `repos` entry, cloned from its `url` and checked out at the commit its `ref` or `pr` resolved to. There is no `repo/` at all without `repos`. |
| `context/` | the `context` zip, extracted (only if `context` is set). |
| `out/` | empty, or with `resume`, the checkpoint's `out/`. The agent's report and files go here (§6). |
| `request.md` | the issue body as claimed. |
| `AIR_TASK.md` | the full task prompt for the agent. |

**Context zip.** `context.url` SHOULD be an asset on the `air-context` release of the requests repo, which
is where `air submit` uploads it (≤ 2 GiB). The requests repo may be private, so a server downloads a
release asset on the requests repo's host through its own GitHub credentials (the release-asset API with
`Accept: application/octet-stream`), and any other URL without credentials. The same holds for every zip
in this spec: `resume.out`, artifacts and report assets. A server MUST:

1. download it once into a single local file, aborting as soon as it exceeds `bytes`;
2. check that file's size and SHA-256 against `bytes` and `sha256`;
3. read the zip's central directory and check every entry before writing anything. Each entry name MUST
   be a relative path (no leading `/` or `\`, no drive letter, no `\` separators) with no `..` segment,
   and it MUST resolve to a path inside `context/`. Each entry MUST be a regular file or directory, so an
   entry whose Unix mode marks it as a symlink (`0o120000`), device or other special file is rejected;
4. before extracting, add up the uncompressed sizes in the central directory and reject the zip if the
   total exceeds the **cap**: 10 GiB or 20 × `bytes`, whichever is smaller;
5. extract only from the file it verified, and stop if the bytes actually written exceed the cap. The
   sizes in the central directory can lie.

No streaming extraction and no second download. A failure at any step fails the request (§8) before the
agent starts, and nothing is extracted.

**Repos.** Before it posts its claim comment (§9), the server makes the `deliver: pr` checks (§6) and
resolves each `repos` entry to a full commit SHA: a `ref` that is a branch or a tag to the commit it names
now, any other `ref` to the full SHA of the commit it abbreviates or names, and a `pr` to the commit
`refs/pull/<pr>/head` names now. An entry that gets a pull request (§6) resolves only if its `ref` is a
branch. The claim comment lists each entry's `path` and SHA. The server records them in its local state and
checks out exactly those commits (detached), at setup and on every restart or resume of this claim, so a
branch that moves meanwhile changes nothing. If an entry can't be resolved, the server doesn't claim. It
comments once per body version and problem (like a lint failure) naming the entry, and the requester fixes
the body.

**Resume.** If the request has `resume`, then before setup the server, for each `branches` entry, fetches
`sha` from that repo's `url` and checks it out in `repo/<path>` on a local branch named `branch`, instead
of the commit the entry's `ref` resolved to. It downloads `resume.out` exactly as a context zip (steps 1 to 5 above, same cap) and extracts it
into `out/`. Any failure fails the request (§8) before setup runs.

**Setup.** `setup` commands and `check` run with `sh -c` in `$AIR_WORKSPACE`, the workspace root, so a
command for one repo starts with `cd repo/<path> &&`. Each runs with stdin from `/dev/null` and with
`AIR_WORKSPACE`, `AIR_CONTEXT` (`$AIR_WORKSPACE/context`) and `AIR_OUT` (`$AIR_WORKSPACE/out`) set.

Each command, `check` included, has a 30-minute timeout. When it expires, the server kills the command's
process group. The setup phase does **not** count against `timeout`, which limits only the agent, so setup
takes at most 30 minutes × (number of `setup` commands + 1). A non-zero exit or a timeout from any `setup`
command or from `check` fails the request (§8) with a comment naming the command, before the agent starts.

When setup passes, the server writes the full task prompt to `AIR_TASK.md` in the workspace root. It then
starts the agent at once, in the same directory, with a short instruction to read that file. `AIR_TASK.md`
MUST tell the agent:

- the workspace layout, including each repo's folder, URL and checked-out commit, and how to deliver
  (§6);
- to keep `out/PROGRESS.md` current as it works: what is done, what is next, and decisions made. The agent
  should also commit work in progress often (WIP commits are fine), since a checkpoint (§11) carries only
  commits and `out/`;
- to create `AIR_DONE` in the workspace root when, and only when, it has finished;
- with `resume`: that it is continuing earlier work, whose state is in `out/PROGRESS.md` and the git log of
  each repo.

The server snapshots the body when it claims; edits made while the issue is claimed are ignored.

## 6. Delivery

The agent finishes by creating `AIR_DONE`. The server then stops the agent's session and delivers as
`deliver` says. Every delivery ends in one **final comment** on the issue, which ends with an `air-result`
block (§10). The agent's report is `out/REPORT.md`.

### `comment`

The server posts the agent's report as an issue comment, followed by the `air-result` block with
`report: comment`. A missing or empty report fails the request (§8). GitHub limits a comment body to
65,536 characters. If the report doesn't fit:

- the server uploads the full text as the asset `air-<N>-<nonce>-report.md` on the `air-artifacts`
  release (see `artifact` below for `<N>` and `<nonce>`);
- it posts a comment that starts with the line `**Truncated:** the full report is in the attached
  artifact.`, then the start of the report, then the `air-result` block with `report: <asset URL>`;
- the report is cut so that the whole comment fits in 65,536 characters.

That asset expires like any artifact (§7). The comment MAY embed images or videos
using `gh issue comment --attach` (gh ≥ 2.99). There is no REST API for this, and it fails with GitHub App
installation tokens, so a server that can't attach links to the files instead. Zips are never sent as
comment attachments: zips go on releases (context above, artifacts below).

### `pr`

Before it claims (§9), the server MUST check, for the `url` of **every** `repos` entry without
`deliver: none`, using `gh api repos/{owner}/{repo}/collaborators/{login}/permission`:

1. that the `url` is on the requests repo's GitHub host, so the checks below can be made;
2. that the **issue author** has `write`, `maintain` or `admin` permission there. Otherwise the server's own
   credentials could push to a repo the requester can't write to;
3. that the **server's own account** has `write`, `maintain` or `admin` permission there, so the work it
   is about to do can be delivered.

If check 1 or 2 fails, the server doesn't claim. It comments once per body version and problem, as for an
entry that can't be resolved (§5), saying which repo and why. If check 3 fails or a check can't be made (an
API error), the server doesn't claim and doesn't comment: another server may be able to serve the request.
A server checks a refused request again on a later poll, since access can change without the body changing.
Read-only entries are not checked: they are only cloned.

The agent commits its work on a branch in each repo it changes. The server doesn't commit for it, and
uncommitted changes are not delivered. For each entry without `deliver: none` whose checkout has commits
beyond the commit its `ref` resolved to, the server pushes branch `air/<N>` to that entry's `url`, where `<N>`
is the issue number. If that branch already exists there, it uses the first of `air/<N>-2`, `air/<N>-3`, …
that doesn't. A resumed request (§11) instead pushes to the branch its `resume` names for that repo. It then
opens one pull request per such repo:

- base: the entry's `ref`;
- title: `air: <issue title> (#<N>)`;
- body: the line `Part of <owner>/<requests-repo>#<N>`, then a blank line and the agent's summary
  (`out/REPORT.md`). Merging a PR never closes the issue: the requester closes it (§8). After opening them
  all, the server adds to each one's body a list of the others, so each PR links to the issue and to its
  siblings. GitHub limits a body to 65,536 characters too: a summary that doesn't fit is uploaded as the
  report asset, as for `comment`, and the body gets the line `**Truncated:** the full report is <asset URL>`
  and the start of the summary instead.

If no repo has such commits, the server opens no PR. Instead it posts a comment saying no changes were
produced and the result is `failed`. That is `failed` rather than `done` because the requester asked for a
change and got none. A failed request also stays visible, and the requester can retry it (§8). Repos without
commits get no PR while others do; the final comment says which ones.

The PRs are the deliverable. The final comment lists their URLs, and its `air-result` block lists them in
`prs`.

### `artifact`

The server zips the regular files and directories under `out/`, except `out/PROGRESS.md`: that is the
agent's notes for resuming (§5), and only a checkpoint (§11) keeps it. Symlinks are neither followed nor
included. If `out/` holds no regular file besides `PROGRESS.md`, the server uploads nothing, comments that
no artifact was produced, and the result is `failed`.

Otherwise it uploads the zip as the asset `air-<N>-<nonce>.zip` on the release tagged `air-artifacts` in
the requests repo. `<N>` is the issue number and `<nonce>` the claim nonce (§9). The final comment
describes the zip, and its `air-result` block holds it in `artifact`, with the same keys and rules as
`context`:

```yaml
artifact:
  url: https://github.com/<owner>/<requests-repo>/releases/download/air-artifacts/air-<N>-<nonce>.zip
  sha256: <64 lowercase hex>
  bytes: <size>
  expires: <YYYY-MM-DD>   # optional
```

## 7. Expiry and `air sweep`

An issue **refers** to a release asset through:

- `context.url` or `resume.out.url` in its body;
- in an `air-result` block (§10) in a comment that counts under §9 (trusted author, never edited):
  `artifact.url`, `resume.out.url`, or `report` when it is a URL.

An asset MUST NOT be deleted while any issue that refers to it is open or carries `air:claimed`,
`air:running` or `air:paused`, whatever its `expires` says. `expires` only sets how long the asset is kept
after that.

Once an issue is closed and has none of those labels, its reference expires on the date given:
`context.expires` for a context zip, or `artifact.expires` for an artifact. With no date, it expires 14 days
after the issue was closed.

`air sweep` deletes an asset when every reference to it has expired, and deletes nothing else. It looks
only at assets on the `air-context` and `air-artifacts` releases of the requests repo. It never deletes:

- assets that no issue refers to;
- anything outside the requests repo;
- media embedded with `--attach`.

`air serve` runs `air sweep` once a day.

## 8. Labels

| Label | Set by | Meaning |
| --- | --- | --- |
| `ai-request` | requester | This issue is a request. Required. |
| `air:claimed` | server | A server won the claim (§9) and is setting up. |
| `air:running` | server | Setup passed; the agent is running. |
| `air:paused` | server | The agent was stopped (operator, quota, reboot); workspace and claim are kept. Back to `air:running` on resume. |
| `air:done` | server | Delivered (`done`). The server closes nothing; the requester closes the issue. |
| `air:partial` | server | Stopped early (§11): the final comment carries the usage and any checkpoint, and the claim is released. |
| `air:failed` | server | Download, clone, setup, check or delivery failed, or `timeout` passed with nothing to checkpoint (`failed`, §11). The server comments why and releases the claim. |
| `air:cancel` | requester | Stop and release. `air cancel` adds it (§12). |

Flow: `ai-request` → `air:claimed` → `air:running` ⇄ `air:paused` → `air:done` | `air:partial` |
`air:failed`. A server replaces one state label with the next. At most one of `air:claimed`, `air:running`,
`air:paused`, `air:done`, `air:partial`, `air:failed` is present.

When it starts, a server creates each of these labels the requests repo lacks, so that a requester can
add `air:cancel` on a fresh repo.

A server MAY claim an issue only if it is open, has `ai-request`, has none of the labels above, is
not past its `deadline`, and no claim currently holds it (§9).

On `air:cancel` the holding server stops the agent, removes its state label, posts a release (§9) whose
`air-result` says `released`, and leaves `air:cancel` in place. No server claims an issue with `air:cancel`.
To offer the issue again, after a cancel, a failure or a partial result, the requester runs `air retry` (§12).

A server MAY release a job that has stayed paused for 48 hours (`released`), so that another server can take
it. A job paused for quota is never released this way: §11 bounds its wait at 24 hours.

## 9. Claiming

Servers coordinate through hidden markers in issue comments. `<host>` matches
`[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, and `<nonce>` is 8 to 64 random `[A-Za-z0-9]` characters, fresh for each
claim.

```
<!-- air-claim v0 host=<host> nonce=<nonce> -->
<!-- air-release v0 host=<host> nonce=<nonce> -->
<!-- air-unsupported v0 host=<host> air=<n> -->
```

A marker **counts** only if all of these hold:

- it is alone on its own line (surrounding spaces allowed);
- it is outside any fenced code block, so a marker quoted in code, in backticks or in prose does nothing;
- the comment's author has write access to the requests repo (§1);
- the comment was never edited (`updated_at` equals `created_at`).

A server writes each marker on its own line. Servers MUST NOT edit comments that carry markers. Anything a
server reports later, such as progress or liveness, goes in a new comment. Text a server quotes (an agent's
report, a log) MUST NOT be able to carry a marker or an `air-result` line that counts: servers defuse such
lines or fence the text.

1. To claim, a server posts a comment containing an `air-claim` marker, a human-readable line, and, for
   each `repos` entry, its `path` and the commit SHA it resolved to (§5). It then waits at least 10 seconds
   and re-reads the comments.
2. The **holder** is the earliest (lowest comment id) counted `air-claim` that isn't ended by a later
   counted `air-release` with the same host and nonce. Claims posted while another claim holds are
   ignored.
3. If its own claim holds, the server adds `air:claimed` and proceeds. If not, it deletes its claim
   comment and moves on.
4. When a server gives up an issue (failure, partial result, cancel, operator release), it posts an
   `air-release` for its claim in its final comment, before the `air-result` block. `air:done` issues are
   not released.

## 10. Results

Every final comment a server posts for a claim holds one `air-result` block: a line holding the
marker `<!-- air-result v0 -->`, then a fenced block with info string `yaml` that holds the fields below in
the YAML subset of §3. A server ends its final comment with the block, but text after the closing fence,
such as a signature or a footer a bot adds, is ignored wherever the block appears. A claim gets exactly one final
comment: on delivery (`done`), on failure (`failed`), on stopping early (`partial`), or on release
(`released`: a cancel, an operator release, a long pause). Other comments, the claim's included, carry no
`air-result`.

````
<!-- air-result v0 -->
```yaml
status: partial
deliver: pr
report: comment
resume:
  branches:
    - repo: service
      branch: air/12
      sha: "0e3c5f4b9a1d2c7e8f6a5b4c3d2e1f0a9b8c7d6e"
  out:
    url: https://github.com/<owner>/<requests-repo>/releases/download/air-artifacts/air-12-<nonce>-out.zip
    sha256: <64 lowercase hex>
    bytes: 18320
usage:
  harness: claude
  tier: large
  before_pct: 41
  after_pct: 100
  attempts: 2
host: anshul-mbp.local
nonce: k3J9xQ2mP7
```
````

| Field | When | Meaning |
| --- | --- | --- |
| `status` | always | `done`, `partial`, `failed` or `released`. |
| `deliver` | always | The request's `deliver`. |
| `prs` | required on `done` with `deliver: pr`, absent otherwise | A non-empty list of maps, `repo` (the entry's `path`, each at most once) and `url` (the pull request), one per PR opened (§6). |
| `artifact` | required on `done` with `deliver: artifact`, absent otherwise | The zip of `out/` (§6): `url`, `sha256`, `bytes`, optional `expires`. |
| `report` | when there is a report | `comment`: the report is the comment's text above the block. Otherwise the URL of the full report's asset (§6). |
| `resume` | `partial` with a checkpoint, absent otherwise | The checkpoint (§11), in the shape of the request field `resume` (§2), so never empty. |
| `usage` | once the agent has started | `harness` (`claude` or `codex`), `tier` (the model tier it ran on), `before_pct` and `after_pct` (percent used of the subscription's weekly window before the first start and after the last stop; omitted when unknown), and `attempts` (how many times the agent was started for this claim). |
| `host`, `nonce` | always | Those of the claim the result belongs to. |

`bytes` and `attempts` are unquoted integers, and `before_pct` and `after_pct` are unquoted numbers from 0 to
100. Unknown keys make the block invalid.

A result **counts** only under the same rules as claim markers, and these:

- the marker line is alone on its line, outside any fenced code block, and it is the only such line in the
  comment: a comment holds exactly one block, so a comment with two holds no result. The next line opens
  the ```` ```yaml ```` fence, and the block ends at the line that closes it. Anything after that line is
  ignored. A result quoted in code or in a block quote does nothing;
- the comment counts under §9: trusted author, never edited;
- the claim with the block's `host` and `nonce` held the issue when the comment was posted, and the same
  account posted that claim. A release in the same comment ends the claim after the result, which still
  counts;
- the claim has no counted result yet: a claim's first counted result is its final one, so a later block for
  the same claim (a `done` claim is never released) does nothing.

The **latest result** of an issue is the counted result with the highest comment id. It is **current** if
no counted claim was posted after it, that is, if no retry has started since.

## 11. Stopping early, checkpoints and resuming

Servers MUST apply these rules while a job runs:

1. **A 5-hour window runs out.** The server pauses the job (`air:paused`) and resumes the agent's session
   after the window resets.
2. **A weekly or monthly window runs out.** If it resets within 24 hours, as rule 1. Otherwise the server
   stops the agent, makes a checkpoint, and posts it as `partial`. A quota pause (rule 1 or 2) that hasn't
   resumed 24 hours after it began, say because the reset time is unknown or the window is still full after
   it, ends the same way, though not before an hour has passed since the reset it waited on.
3. **The agent exits without `AIR_DONE`**, whatever its exit status: it crashed, hit an API error, or
   someone quit it. The server resumes the agent's own session **once**, telling it to read
   `out/PROGRESS.md` and the git log and to continue. If that session can't be resumed, a fresh start with
   the same instruction takes its place. If it exits without `AIR_DONE` again, the server makes
   a checkpoint and posts `partial`. Running out of context is not a cut-off: agents compact their context
   and carry on. Closing the agent's window or `air stop` is an operator pause, not an exit.
4. **The job costs more than twice its effort's dollars** (§2), its agent's tokens priced at API rates.
   The server stops the agent, makes a checkpoint, and posts `partial` with the usage. A server that can't
   measure the job's tokens doesn't apply this rule, and tokens on a model it has no price for count as
   nothing.
5. **`timeout` passes.** The server stops the agent and makes a checkpoint. The result is `partial` if the
   checkpoint holds anything, else `failed`.

A **checkpoint** keeps the work so far:

- with `deliver: pr`, for each `repos` entry without `deliver: none` that has commits beyond the commit its
  `ref` resolved to, the agent's branch is pushed as in §6: `air/<N>`, the next free `air/<N>-<k>`, or a
  resumed request's checkpoint branch,
  with no pull request. Work-in-progress commits are pushed as they are, and
  uncommitted changes are left out. Only `deliver: pr` pushes, since only there was write access checked;
- `out/`, if it holds a regular file, is zipped as for `deliver: artifact`, but with `out/PROGRESS.md`
  included, since the resumed agent reads it, and uploaded as the asset `air-<N>-<nonce>-out.zip` on the
  `air-artifacts` release.

The `partial` final comment says why the job stopped and what the checkpoint holds. Its result carries
`usage`, `report: comment`, and `resume` if the checkpoint holds anything. The comment also releases the
claim (§9), and the label becomes `air:partial`.

**Resuming.** A request whose front matter has `resume` (§2) continues a checkpoint: the server sets up
from its branches and `out/` (§5), and `AIR_TASK.md` tells the agent it is continuing earlier work.
Otherwise it is served like any request, by any server. Its work stays on the checkpoint's branches: for
each `resume.branches` entry, the pull request (§6) or the next checkpoint pushes to `branch` itself, not to
a new `air/<N>-<k>`, so no branch is left behind. The push moves the branch on only if it still points at
the checkpoint's `sha` (or is gone). If someone moved it meanwhile, the server leaves it alone and that repo
gets no push, as a repo without commits; the final comment says why.

## 12. Requester commands

These are `air` commands for requesters. Each reads the issue and its comments with the requester's own
`gh` credentials, and trusts only counted markers and results (§9, §10). Every `air` command exits 2 on a
usage error (a bad flag or argument).

- **`air status N [--json]`** prints the issue's state label, the current holder (host) if any, and the
  latest result with its PRs, artifact, checkpoint and usage. It says when that result is not current. It
  changes nothing. `--json` prints the same as one JSON object, with the result's fields as the block names
  them, plus `comment_id` and `current`.
- **`air wait N [--timeout D] [--json]`** reads issue `N` every 30 seconds until it has a current latest
  result (§10), then prints it as `air status` does. `D` is a duration written like `timeout` (§2); without
  it, `air wait` waits for ever. It exits 0 for `done`, 3 for `partial`, 1 for `failed` or `released`, and
  4 when `D` passes first, after printing the status as it is. It also exits 1 if it can't read the issue;
  GitHub server errors, rate limits and timeouts while polling are retried at the next poll instead.
- **`air fetch N [DIR]`** fetches the latest result into `DIR` (default `./air-<N>`), which must not exist
  or must be empty. It lays the result out like a workspace (§5):
  - the report, if the result has `report`, to `DIR/REPORT.md`: for `report: comment`, the comment's text
    above the block, without the marker lines that count (§9); for a URL, the downloaded asset. Without
    `report`, no `REPORT.md` is written;
  - for each entry in `prs`, the pull request's head branch, checked out in `DIR/repo/<repo>`. The pull
    request must be on the requests repo's GitHub host;
  - the `artifact`, downloaded, checked against `bytes` and `sha256`, and extracted into `DIR/artifact/`
    under the zip rules of §5;
  - for a `partial` result, each `resume` branch cloned from the `url` of the `repos` entry whose `path` it
    names (in the body as it is now), checked out at its `sha` on a local branch named `branch` in
    `DIR/repo/<repo>`, and `resume.out` downloaded, checked and extracted into `DIR/out/` in the same way.

  A size or hash mismatch, or a zip entry that breaks the §5 rules, is an error, and nothing more is
  extracted. A result that is not current is fetched all the same, with a note.
- **`air cancel N`** cancels the request by adding `air:cancel` (§8), creating the label first if the
  repo lacks it. Only the issue's author, or an account with write access to the requests repo (§1), may
  run it. It refuses for an issue that is closed or has no `ai-request` label.
- **`air retry N [--effort L]`** offers the request again. Only the issue's author, or an account with
  write access to the requests repo (§1), may run it. It refuses while a claim holds the issue, and for an
  issue that is closed or has no `ai-request` label. If the latest result is `partial` with `resume`, it
  sets the front matter's `resume` to that (replacing any earlier one); otherwise it leaves `resume` as it
  is. With `--effort`, it sets `effort` to `L`. It refuses if the body doesn't pass `air lint`, before or
  after these edits. It edits the body first, then removes every `air:*` label (`air:cancel` included), so
  no server can claim the old body.

## 13. Versioning

This is version 0: requests say `air: 0`, and markers say `v0`. A server ignores a request with any other
`air`, apart from one comment per host and version carrying an `air-unsupported` marker.
